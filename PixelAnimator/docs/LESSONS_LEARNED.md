### [2026-08-26] [PixelAnimator] - LLMにピクセルアートを描かせる方式の選定
- **問題**: 「高品質なドット絵アニメーションをAIエージェントに作らせる」という要求に対し、
  画像生成モデル（DALL-E/Stable Diffusion系）を使うか、LLMに直接ピクセルデータを
  生成させるかの選択が必要だった。
- **原因**: 画像生成APIは外部キー・コスト・レート制限が別途必要になり、既存リポジトリの
  「Vanilla JS + Canvas2D」構成との親和性も低い。
- **解決策**: Claude の tool use（構造化出力）で `{ palette: string[], frames: { pixels: number[][] }[] }`
  を直接生成させ、アプリ側の Canvas でレンダリングする方式を採用した。
  `tool_choice` を forced にすることで、自由テキストではなく必ず指定スキーマの
  JSON が返るようにしている。
- **教訓**: LLMにビットマップそのものを描かせたい場合、画像生成APIを挟まなくても
  「パレットindexの2次元配列」という軽量な構造化出力で十分実用的な結果が得られる。
  特に小さい解像度（16〜48px四方）のドット絵とは相性が良い。
- **関連ファイル**: `aiClient.js`

  direct-browser-access ヘッダが、バックエンドなしで動く現実的な選択肢になる。

### [2026-08-27] [PixelAnimator] - 「ユーザーの確認・修正回数を減らす」ための自己チェックループ
- **問題**: 初期実装は「1回生成→人間が見て良し悪しを判断→気に入らなければ手動で
  再生成やフレーム単位の修正を指示」という、人間の確認・判断が前提の設計だった。
  しかし本来の目的は「AIエージェント自身が自律的に作成・確認・修正まで完結し、
  ユーザーのチェック回数・修正回数を減らすこと」だった。
- **原因**: LLMのtool useで一発生成する方式は品質のばらつきが大きく（空白フレーム、
  フレーム間の不整合、色の破綻など）、それを検出・修正する主体がユーザーしかいない
  設計だと、結局ユーザーが毎回チェック係になってしまう。
- **解決策**: `generateWithSelfCheck()` を新設し、
  1. 生成（`emit_pixel_animation`）
  2. コード側の機械的チェック（`qa.js` の `runHeuristicChecks` — 空白フレーム・
     パレット未使用・フレーム間の不整合・ループ不整合をAPI呼び出しなしで検出）
  3. Claudeの画像入力を使った自己批評（`emit_critique` — 生成物をスプライトシート
     画像として自分自身に見せて採点・具体的な修正指示を出させる）
  4. 問題があれば指摘事項をフィードバックとして次の生成プロンプトに織り込み、
     最大イテレーション回数（既定3）まで自動的に再生成
  というループに置き換えた。ユーザーには「エージェントログ」として経過が流れるのみで、
  判断を求めるのは上限到達時（`verdict: 'needs_review'`）だけにした。
- **教訓**: 「AIに作らせる」だけでなく「AIに自分の成果物を検証・修正させる」ところまで
  ループに組み込むと、人間のレビューコストは劇的に下がる。特に画像生成のように
  出力の良し悪しが視覚的にしか判断できないタスクでは、①コストゼロで判定できる
  機械的ヒューリスティックと、②実際に画像を見て評価する視覚モデルの自己批評、を
  組み合わせるのが費用対効果が良い（ヒューリスティックで安く弾ける問題は先に弾き、
  視覚モデルの呼び出し回数を減らす）。
- **関連ファイル**: `aiClient.js`（`generateWithSelfCheck`, `critiqueAnimation`）,
  `qa.js`, `exporter.js`（`getReviewSpritesheetBase64`）, `main.js`（エージェントログ表示）

### [2026-08-27] [PixelAnimator] - APIキーからサブスクリプション直結（Claude Code CLI）への切り替え
- **問題**: ユーザーから「APIは使わず、サブスクのプランで直接操作させたい」という
  明確な要望があった。それまでの実装はAnthropic APIキーをユーザー自身に発行させ、
  `localStorage`に保存してブラウザから直接REST APIを叩く方式で、従量課金のAPIキーが
  別途必要だった。
- **原因**: ブラウザ単体のJavaScriptからは子プロセスを起動できないため、
  「ローカルにログイン済みのClaude Code CLI（サブスクリプション認証）」を使うには
  ブラウザ以外の実行主体が必要だった。
- **解決策**: Viteの開発サーバーに `configureServer` ミドルウェアプラグイン
  （`vite.config.js`）を追加し、`server/claudeApi.js`（Node専用）が
  `child_process.execFile('claude', [...])` でローカルの `claude` CLIを子プロセスとして
  起動する構成にした。CLIには `--json-schema` で構造化出力スキーマを、
  `--system-prompt` でシステムプロンプトを、`--model` でモデルを指定でき、
  戻り値の `structured_output` フィールドにパース済みJSONが入っている
  （`--output-format json` 使用時）。画像入力（自己レビュー）は、base64画像を
  一時ファイルに書き出し、`--allowedTools Read --add-dir <tmpdir> --permission-mode dontAsk`
  でCLIの `Read` ツールに読ませることで実現した。CLIの認証はユーザーがターミナルで
  `claude login` した際のOAuthをそのまま使うため、Anthropic APIキーは完全に不要になった。
  ブラウザ側（`aiClient.js`）は `callClaude()` の中身を「Anthropic REST APIへのfetch」から
  「`/api/claude` へのfetch」に差し替えるだけで済み、`generateWithSelfCheck()` を含む
  上位のロジックはほぼ無改修だった（サーバーが返すレスポンス形をAnthropicの
  tool_use形式 `{content:[{type:'tool_use', name, input}]}` に合わせたため）。
- **教訓**: 「ブラウザ完結」と「ローカルCLIのサブスクリプション認証を使う」は両立しない
  （子プロセス起動が必須になる）。ただし、上位のプロンプト構築・スキーマ検証・自己チェック
  ループのロジックを「レスポンス形状」で抽象化しておけば、トランスポート層（REST API直叩き
  ↔ ローカルCLI経由）の差し替えは驚くほど局所的な変更で済む。また `claude` CLIの
  `--json-schema` は Anthropic APIの forced tool_choice と同等の「必ずこの形式で返す」
  保証を、ヘッドレスモードでも提供してくれる（実際に本物のCLIで動作確認済み）。
  `--bare` フラグは認証を `ANTHROPIC_API_KEY` のみに制限してしまう（OAuth/keychainを
  読まない）ため、サブスクリプション認証を使いたい場合は絶対に付けてはいけない。
- **関連ファイル**: `server/claudeApi.js`, `vite.config.js`, `aiClient.js`（`callClaude`）,
  `index.html`（設定ダイアログからAPIキー欄を削除しCLI接続確認ボタンを追加）

### [2026-08-27] [PixelAnimator] - 再生成を「白紙からの描き直し」から「実データを見せての修正」に変更
- **問題**: 実機テストで、自己チェックが「フレーム間でリンゴの重心がズレている」という
  同じ種類の指摘を3イテレーションとも繰り返し、スコアが6/10で頭打ちになった。原因を
  調べると、再生成のたびに `generateAnimation()` を「元の発注内容＋指摘事項のテキスト」
  だけで最初から呼び直しており、モデルは前回自分が実際に描いたピクセル配置を正確には
  覚えていない（テキストの記憶だけを頼りに毎回ゼロから描き直している）状態だった。
- **原因**: フィードバックを「次はこう直してね」という自然文でdescriptionに追記するだけの
  設計だと、モデルは「具体的にどのピクセルが今どこにあるか」を正確に把握できないまま
  再生成することになり、同じ種類のズレを作り込んでしまう（あるいは別の場所を壊す）。
- **解決策**: `refineAnimation()` を新設。2回目以降のイテレーションでは、直前の
  生成結果（パレット・全フレームの実ピクセルデータ）をそのままJSONとしてプロンプトに
  埋め込み、「これを出発点として指摘箇所だけをピクセル単位で直せ、無関係な部分は
  変えるな」と明示的に指示するようにした。`generateWithSelfCheck()` は
  `priorResult`（直前の生成結果）と `issuesToFix`（ヒューリスティック or 画像レビューで
  見つかった問題文の配列）を保持し、2回目以降は `generateAnimation()` ではなく
  `refineAnimation()` を呼ぶよう分岐する。Playwrightでfetchをモックし、
  「1回目=fresh generate」「2回目以降=現在の全フレームを含むrefine呼び出し」に
  なっていることを検証済み（全チェック合格）。
- **教訓**: 画像生成に限らず、LLMに「前回の出力を直させる」タスクをやらせるときは、
  自然文のフィードバックだけに頼らず、**前回の実際の出力データそのものをコンテキストに
  含める**方が収束が速い。特にピクセル単位・座標単位のような「正確な現状把握」が
  修正の前提になるタスクでは、記憶に頼った再生成は同じ誤りを再生産しやすい。
- **関連ファイル**: `aiClient.js`（`refineAnimation`, `generateWithSelfCheck`）

### [2026-08-27] [PixelAnimator] - リクエスト中断時の子プロセット孤児化を防止
- **問題**: 実機テストの初回試行でPlaywrightスクリプトのバグにより `page.waitForFunction`
  が30秒でタイムアウトしてスクリプトが異常終了した際、`ps aux` で確認すると
  `claude -p ...` の子プロセスが2つ同時に走っていた。片方は打ち切られたはずの
  前回リクエストの残骸（孤児プロセス）だった。
- **原因**: `server/claudeApi.js` の `execFile` 呼び出しに中断の仕組みがなく、
  HTTPリクエスト側（ブラウザのタブが閉じられる・ページ遷移する等）が切断されても
  子プロセスは走り続ける実装になっていた。
- **解決策**: `vite.config.js` のミドルウェアで `AbortController` を作成し、
  `req.on('close', () => abortController.abort())` で接続断を検知。
  `execFileAsync` に `signal` オプションとして渡すことで、Node標準の
  `child_process` の中断機構（Node 15.4+）を使って子プロセスごと確実に終了させる
  ようにした。あわせて、中断後にレスポンスを書き込もうとしてエラーになるのを防ぐため
  `res.writableEnded` のガードも追加した。
- **教訓**: ローカルの長時間CLIプロセスをHTTP経由でラップするときは、
  「クライアントが去った後もプロセスが残り続けないか」を最初から設計に入れる。
  Node標準の `AbortController`/`AbortSignal` は `child_process` 系のAPIと素直に
  組み合わせられる。
- **関連ファイル**: `server/claudeApi.js`, `vite.config.js`

### [2026-08-27] [PixelAnimator] - refine方式を実機で再検証: 部分的に有効、新たな退化パターンを発見
- **問題**: `refineAnimation()`（実データを見せて修正させる方式）導入後、同じ「赤くて
  丸いリンゴ」のお題で実機の `claude` CLIを使い再検証したところ、スコアは
  4/10 → 6/10 → 3/10 と推移し、単調には改善しなかった。特にイテレーション3では、
  「フレーム間の一貫性がない」という指摘（本来は形状・重心のズレを直してほしいという
  意図）に対し、AIが**2フレームをほぼ完全に同一にする**ことで「一貫性」を満たそうとし、
  結果として上下運動そのものが消えてしまうという新しい退化パターンが発生した
  （発注内容の核心要求である「動きが見える」ことを犠牲にして、指摘された言葉面だけを
  満たす近道を取ってしまった）。
- **原因**: (1) `refineAnimation()` のプロンプトが「指摘箇所だけ直せ、関係ない箇所は
  維持しろ」とは言っていたが、「フレームを同一にして誤魔化すのは禁止」という明示的な
  ガードレールがなかった。(2) `qa.js` の一貫性チェックが `diff === 0`（完全一致）
  でしか近似同一を検出しておらず、「ほぼ同一（数%だけ違う）」という今回のような
  ケースを安価なヒューリスティック段階で弾けず、高コストな画像レビューまで
  問題が持ち越されていた。
- **解決策**: 2点を修正。①`qa.js` の一貫性チェックを `diff === 0` から
  `diff < 0.03`（3%未満）に変更し、「ほぼ同一」もAPI呼び出し不要の段階で検出して
  即座にフィードバックに回せるようにした（`NEAR_DUPLICATE_THRESHOLD`）。
  ②`refineAnimation()` のプロンプトに「一貫性の指摘への対処としてフレームを
  ほぼ同一にするのは禁止。動きが明確に分かる状態を維持すること」という
  ガードレール文を追加した。単体テスト（Node直接実行、ブラウザ不要）で
  1px変化・0px変化のケースが正しく検出され、7.8%変化の正当な動きは
  誤検出しないことを確認済み。
- **教訓**: 自己批評ループでAIに「一貫性を保て」「問題Xを直せ」と指摘すると、
  指摘の言葉面だけを満たす最も安易な解（今回は「差分をなくす」）に流れる
  リスクが常にある。批評・修正のプロンプトには、**何を犠牲にしてはいけないか
  （ここでは「動きが見えること」）を明示的に列挙する**必要がある。また、
  「ほぼ同じ」を検出するヒューリスティックは、完全一致だけでなく閾値付きの
  近似判定にしておかないと、退化を安く早期に捕まえられない。
- **関連ファイル**: `qa.js`（`NEAR_DUPLICATE_THRESHOLD`）, `aiClient.js`（`refineAnimation`）

### [2026-08-27] [PixelAnimator] - 実機再検証テストで判明: `req.on('close')` は即座に発火する
- **問題**: 「リクエスト中断時の子プロセス孤児化を防止」の修正を入れた直後、実機での
  リンゴ生成テストが一切完了しなくなり（`curl` で単発リクエストを送ると
  ほぼ0秒で「中断されました」エラーが返る）、機能そのものが壊れていた。
- **原因**: `vite.config.js` で `req.on('close', ...)` を使っていたが、Node.jsの
  `http.IncomingMessage`（＝`req`）の `'close'` イベントは「クライアントが
  切断したとき」ではなく「**リクエストボディの読み込みが完了したとき**」にも
  発火する。POSTボディが小さければ一瞬で読み終わるため、CLI呼び出しを
  開始する前に誤ってabortしてしまっていた。
- **解決策**: `res.on('close', ...)`（`http.ServerResponse` 側）に変更し、
  かつ `!res.writableEnded` の場合のみabortするようガードした。`res` の
  `'close'` はレスポンス完了後にも発火するため、「まだ書き終えていないのに
  接続が切れた」場合だけを正しく判別できる。curlで(1)正常完了時に子プロセスが
  結果を返すこと、(2)`timeout` コマンドで途中切断した際に子プロセスが確実に
  終了することの両方を実機で確認済み。
- **教訓**: Node.jsの `req`（IncomingMessage）と `res`（ServerResponse）の
  `'close'` イベントは名前が同じでも意味が異なる。「クライアント切断」を
  検知したい場合は `res.on('close')` を使い、`res.writableEnded` で
  正常完了と区別すること。**この種のエッジケース（中断・エラー系）は
  モックしたテストでは絶対に検出できない**ため、必ず実際のサーバーに
  対してリクエストを送る形で検証する必要がある（このバグもモックの
  自動テストは全て通過していたが、実機テストで即座に発覚した）。
- **関連ファイル**: `vite.config.js`

### [2026-08-27] [PixelAnimator] - 「主役はAIエージェント、人間ではない」という要件でCLIを新設
- **問題**: ブラウザUI＋自己チェックループを一通り作った後、ユーザーから
  「作りたいのはドット絵の作成ではなくドット絵アニメーションの作成で、もっと
  踏み込んだ機能が必要」「人間というよりAIのためのツール」「人間はちょっとした
  手直しや確認レベルにしたい」という明確な方向修正があった。それまでの実装は
  「人間がブラウザでボタンを押し、裏でAIが生成する」設計であり、AIエージェント
  自身がこのツールを直接・自律的に操作する手段が存在しなかった。
- **原因**: 生成ロジック（`generateWithSelfCheck` 等）がブラウザの `fetch`・
  `localStorage`・Canvas（`document.createElement('canvas')`）に直接依存しており、
  ブラウザなしでは一切呼び出せない構造になっていた。
- **解決策**: 大規模なリファクタリングを実施。
  1. プロンプト構築・スキーマ検証・自己チェックループ本体を `core.js` として
     DOM/fetch/localStorage非依存で切り出した（`callClaude` と `renderReviewImage`
     を呼び出し側が注入する設計）。
  2. ブラウザ版 `aiClient.js` は `core.js` にfetchベースの `callClaude` と
     CanvasベースのrenderReviewImageを注入する薄いアダプタに変えた。
  3. Node版 `server/agentCore.js` を新設。`handleClaudeApi()` をHTTPを介さず
     インプロセスで直接呼ぶ `callClaude` と、`pngjs`（Canvas不使用の純粋JS PNG
     エンコーダ）で自己レビュー画像を組み立てる `renderReviewImage` を注入する。
  4. `server/pngRender.js` を新設。`pngjs` で等倍スプライトシートPNGと拡大市松模様の
     レビュー画像を、`gifenc`（元々DOM非依存）でGIFを、いずれもCanvas無しで生成する。
  5. `cli.js` を新設。`node cli.js generate --prompt "..." --out <path>` の1コマンドで
     生成〜自己チェック〜ファイル書き出しまで完結する。stdoutは機械可読なJSON
     （`verdict`/`score`/`iterations`/`files`）のみ、進行状況ログは全てstderrへ。
     終了コードで成功(0)/エラー(1)/要確認(2)を区別し、エージェントが `$?` で
     分岐できるようにした。
  - 実機（本物の `claude` CLI）で `node cli.js generate` を**ブラウザ・Vite開発
    サーバーなしで直接実行**し、1回目が5/10で自動的にrefineへ進み、2回目に

### [2026-08-27] [PixelAnimator] - 同一キャラクターの複数アクションセット生成（character サブコマンド）
- **問題**: 単発の `generate` だけでは、ゲームで実際に使う「同じキャラクターの
  idle/walk/attack等、複数アクション」を一貫したスタイル・配色で揃えられなかった
  （呼ぶたびに独立生成のため、色や体型が微妙にズレるリスクがある）。
- **解決策**: `cli.js character` サブコマンドを新設。まず基準ポーズ（1枚絵、
  `frameCount:1, loopMode:'once'` で `generateWithSelfCheck` を流用）を確定させ、
  それを `core.js` の `reference` 機構（`generateAnimation` の初回呼び出しにのみ
  注入され、パレット・ピクセルグリッドをそのままプロンプトに埋め込む）で各アクションの
  生成に見せることで一貫性を保つ。各アクションは独立した自己チェックループを持ち、
  1つのアクションで実行時エラー（タイムアウト等）が起きても他のアクションの結果は
  失われず、`character.json` にエラー内容が記録される設計にした。
- **実機検証**: 「青いぷるぷるスライム」で `idle`+`hop` の2アクションを実際に生成。
  基準ポーズとidleアクションはどちらも1回目で自己チェック合格（8/10）、
  見た目も同一キャラクターとして視覚的に一貫していることを確認。hopアクションは
  2回目の生成でCLIタイムアウト（後述）が発生したが、**他の成果物は正常に書き出され、
  character.jsonにエラーが記録され、プロセス全体はクラッシュしなかった**——設計通りの
  部分的失敗の分離ができていることも実地で確認できた。
- **教訓**: バッチ的な複数生成では「1件の失敗で全体を巻き込まない」設計が重要。
  各ステップを独立したtry/catchで囲み、成功した分の成果物は必ず保存し、
  失敗はサマリーに記録する（例外を握りつぶさない）ことで、AIエージェントが
  部分的な結果からでも次の判断（そのアクションだけ再実行する等）を取れるようにする。
- **関連ファイル**: `cli.js`（`runCharacterCommand`）, `core.js`（`reference`/`buildReferenceBlock`）

### [2026-08-27] [PixelAnimator] - 「ドット絵らしく見えること」を最優先の明示的ゲートにする
- **問題**: ユーザーから「ドット絵でそれらしく見えるというのがいちばんのキモです」と
  明確な優先度の指摘があった。それまでの自己批評（`emit_critique`）は `score` という
  単一の holistic な指標にすべてを混ぜ込んでおり、「技術仕様は満たすが本物のドット絵に
  見えない」という失敗モードを見逃しうる設計だった。
- **解決策**: 2段構えで対応。
  1. `STYLE_GUIDE` の冒頭に「ドット絵らしく見えるための絶対ルール（最優先）」という
     セクションを新設し、孤立ノイズピクセルの禁止・面のまとまり・意図的な階段状輪郭・
     パーツの統一感、を具体的に明記した（生成・refine・critique全てに効く）。
  2. `emit_critique` のスキーマに `pixelArtAuthenticity`（1-10、最重要項目）を
     `score` とは別の必須フィールドとして追加し、「両方が7以上でなければapprove
     しない」とプロンプトで明示。**さらにコード側（`critiqueAnimation()`）でも
     同じ基準を強制**し、モデルが指示を無視して `pixelArtAuthenticity` が低いのに
     `verdict:'approve'` を返した場合は `needs_fix` に強制的に上書きする
     二重のガードにした。
- **検証**: (a) Node単体実行で `pixelArtAuthenticity` が生成・CLI出力・stdout JSONまで
  一貫して伝播することを確認（実機、「緑のキノコアイテムアイコン」で
  score8/10・authenticity8/10、実際に輪郭のはっきりした認識しやすいアイコンが生成された）。
  (b) Playwrightでfetchをモックし、モデルが `score:9, pixelArtAuthenticity:3` で
  `approve` と言い張るケースを再現 → コード側ガードが正しく `needs_fix` に
  上書きし、最終的に3回試行後 `needs_review` へ落ちることを確認（モデルが
  プロンプト指示を無視しても壊れない防御になっていることを実証）。
- **教訓**: 「一番重視してほしい品質軸」がある場合、それをholisticなスコアの一部に
  混ぜ込むのではなく、**専用のフィールドとして分離し、承認条件の明示的なゲートにする**
  方が確実。さらに、LLM評価者がプロンプトの指示（「両方7以上でなければapproveしない」）
  を守るとは限らないため、**コード側でも同じロジックを冗長に強制する**（人間の
  信頼だけに頼らない）ことで、指示違反があっても不良品が承認されるのを防げる。
- **関連ファイル**: `core.js`（`STYLE_GUIDE`, `buildCritiqueToolSchema`, `critiqueAnimation`）,
  `cli.js`・`main.js`（ログ・サマリーへの`pixelArtAuthenticity`反映）
