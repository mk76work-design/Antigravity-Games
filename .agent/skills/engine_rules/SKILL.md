# Engine Rules スキル

AIエージェントがコードを生成する際に従うべき、ゲームエンジン / フレームワーク固有のルールを管理する。
頻繁なAPI変更による古いコード出力（ハルシネーション）を防止し、
アーキテクチャ負債の蓄積を予防するための包括的な仕組み。

---

## フレームワーク親和性基準

AIエージェントが高い自律性を発揮できるフレームワークには以下の条件がある。
技術スタック選定時、この基準を参考にすること。

### ✅ AI親和性が高い条件

| 条件 | 説明 |
|------|------|
| **Code-First（コード中心）** | ロジック・UI配置・シーン構造がすべてテキストで定義される |
| **ボイラープレート最小化** | 数十行でゲームループを立ち上げられる高い抽象化 |
| **コンポーネント指向** | 重力・衝突判定・入力処理を独立モジュールとして付与可能 |
| **テキストシリアライゼーション** | シーン構造がプレーンテキストで保存される |

### ❌ AI親和性が低い条件

| 条件 | 問題 |
|------|------|
| **ビジュアルノードベース** | GUIエディタ操作がテキストI/Oモデルと不整合 |
| **大量のボイラープレート** | 初期化に数百行を要しコンテキストを浪費 |
| **暗黙的な設定** | XMLやバイナリフォーマットでの設定ファイル |

### 推奨フレームワーク適合度

| フレームワーク | AI親和性 | 理由 |
|--------------|---------|------|
| **Kaboom.js** | ⭐⭐⭐⭐⭐ | 最小ボイラープレート、`body()`/`solid()` 等の宣言的コンポーネント指向 |
| **Vanilla Canvas 2D** | ⭐⭐⭐⭐ | 完全なコード中心、抽象化はないが柔軟 |
| **Three.js** | ⭐⭐⭐ | 3D開発の標準、ただしAPIが広大 |
| **Godot (GDScript)** | ⭐⭐⭐⭐ | Pythonに似た軽量言語、テキストシリアライゼーション (.tscn) |
| **Phaser.js** | ⭐⭐⭐ | 豊富な機能、ただしAPIが広大でコンテキスト消費が多い |
| **Unity (C#)** | ⭐⭐ | GUIエディタ依存度が高い |
| **Unreal (Blueprint)** | ⭐ | ビジュアルノードベースでAIに不適 |

## アーキテクチャ負債防止ルール（全フレームワーク共通）

> AIエージェントは「博士号を持つジュニアエンジニア」であり、
> 「とりあえず動かすこと」を優先し力技による解決を図る傾向がある。
> 以下のルールでアーキテクチャ負債の蓄積を防止する。

### 絶対ルール

| # | ルール | 理由 |
|---|--------|------|
| 1 | **1ファイル最大300行** | コンテキストウィンドウの節約、モジュール性の維持 |
| 2 | **1関数最大30行** | 個別関数のコンテキスト負荷軽減 |
| 3 | **グローバル変数の使用禁止** | 名前衝突、デバッグ困難、暗黙的な依存 |
| 4 | **ハードコーディング禁止** | 定数は設定オブジェクトまたは設定ファイルに集約 |
| 5 | **DRY原則の徹底** | 3回以上出現するロジックは関数に抽出 |
| 6 | **各モジュールに明確なインターフェース** | `export`/`import` で依存を明示 |

### 300行超過時の対応
ファイルが300行を超えた場合、以下の分割パターンに従う：

```
❌ game.js (500行) — モノリシック

✅ 分割後：
├── main.js (100行)     — ゲームループ・初期化
├── player.js (120行)   — プレイヤーロジック
├── enemy.js (80行)     — 敵AI
├── ui.js (100行)       — UI/HUD
└── config.js (50行)    — 定数・設定値
```

## ルールファイルの構造

`rules/` ディレクトリ内にMarkdownファイルとしてルールを配置する：

```
engine_rules/
├── SKILL.md              ← このファイル（全体の説明）
└── rules/
    ├── README.md          ← ルールファイルの追加・管理ガイド
    └── web_game_rules.md  ← Webゲーム開発ルール
```

### ルールファイルの追加方法
新しいゲームエンジンやフレームワークに対応する場合は `rules/` に追加する：

```
rules/
├── web_game_rules.md       ← HTML5/Canvas/WebGL（初期添付）
├── kaboom_rules.md         ← Kaboom.js 固有ルール（必要に応じて追加）
├── threejs_rules.md        ← Three.js 固有ルール（必要に応じて追加）
├── godot_rules.md          ← Godot 固有ルール（必要に応じて追加）
└── phaser_rules.md         ← Phaser.js 固有ルール（必要に応じて追加）
```

## エージェントへの指示

### コード生成前に必ず実行すること
1. プロジェクトで使用している技術スタックを確認する
2. **フレームワーク親和性基準**を参照し、AI適性の高い技術を選定する
3. 該当する `rules/` ファイルを**必ず読み込む**
4. ルールに違反するコードを生成してはならない

### ルールの優先順位
1. `rules/` 内のプロジェクト固有ルール（最優先）
2. 本ファイルのアーキテクチャ負債防止ルール
3. 公式ドキュメントの最新API仕様
4. エージェントの学習データ（最低優先 — 古い情報の可能性あり）

### ハルシネーション防止チェックリスト
コード生成時に以下を確認する：
- [ ] 使用するAPIは `rules/` ファイルに記載されたバージョンに準拠しているか
- [ ] 非推奨（deprecated）のAPIを使用していないか
- [ ] `rules/` ファイルの「禁止パターン」に該当するコードがないか
- [ ] ライブラリのインポート方法が正しいか（CDN URL、バージョン指定）
- [ ] **ファイルが300行以内**か
- [ ] **グローバル変数を使用していない**か
- [ ] **ハードコーディングされた定数がない**か

## ルールファイルのメンテナンス

### 更新が必要なタイミング
- ライブラリのバージョンアップ時
- 新しいベストプラクティスが確立された時
- ハルシネーションが発生した場合（問題のあるパターンを禁止ルールに追加）
- `LESSONS_LEARNED.md` に蓄積された教訓に基づく更新

### ルールファイルのフォーマット
```markdown
# [技術名] ルール

## バージョン情報
- 対象バージョン: X.Y.Z
- 最終更新: YYYY-MM-DD

## 推奨パターン
（コード例付きで推奨パターンを記述）

## 禁止パターン
（コード例付きで禁止パターンとその理由を記述）

## CDN / インポート
（正しいインポート方法とバージョン固定のURL）

## パフォーマンスガイドライン
（技術固有のパフォーマンス改善策）
```
