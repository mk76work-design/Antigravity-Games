# Game Dev Workflow スキル

ゲーム開発においてAIエージェントが従うべきワークフローを定義する。
本スキルは、スタンフォード大学のACE（Agentic Context Engineering）フレームワーク、
スペック駆動型開発（SDD）、およびContext Architect（CA）プロトコルの原則に基づき設計されている。

---

## ⚠️ 絶対原則：Vibe Coding の禁止

> **「スーパーマリオのようなゲームを作って」といきなりコードを生成させることは厳禁である。**

AIエージェントは「博士号を持つジュニアエンジニア」である。構文記述能力は卓越しているが、
長期的なソフトウェア設計の知恵を欠いている。直感的なプロンプトからいきなりコードを生成する
「Vibe Coding」は、以下の問題を必ず引き起こす：

- **アーキテクチャ負債の蓄積**: グローバル変数の乱用、ハードコーディング
- **リグレッションの連鎖**: あるバグ修正が別のシステムを破壊する
- **コンテキスト・ロット**: モデルが混乱し幻覚（ハルシネーション）を起こす

**代わりに、スペック駆動型開発（SDD）に従う：**
1. まずAIと対話しながら仕様書（spec / implementation_plan）を作成する
2. 要件・アーキテクチャ・設計判断を完全に文書化する
3. 人間がレビュー・承認してからのみ、コードの実装を許可する

---

## 0. Context Architect プロトコル（全フェーズ共通）

> **すべての作業は「Read → Execute → Update」のループで実行する。**
> ドキュメントを「外部脳」として活用し、会話を跨いでも文脈を維持する。

### Step 0: Context Sync（作業開始前 — 必須）

```
Action: 対象ゲームプロジェクトの docs/ 内ドキュメントを読み込む
  1. docs/PROJECT_STRUCTURE.md  → 現在のファイル構成を把握
  2. docs/REPO_MAP.md           → 関数・クラスの依存関係を把握
  3. docs/LESSONS_LEARNED.md    → 過去の教訓・失敗パターンを確認

Constraint:
  - これらのドキュメントと矛盾する作業は行わない
  - 情報が古い場合は、まず現状を確認するプロセスを挟む
  - Knowledge Base（LESSONS_LEARNED.md）に記載された過去の失敗を繰り返し提案してはならない
```

### Step Final: State Persistence（作業終了前 — 必須）

```
Action: 対象ゲームプロジェクトの docs/ 内ドキュメントを更新する
  1. 完了したタスクを task.md から削除/チェック
  2. 変更された構造を docs/PROJECT_STRUCTURE.md に反映
  3. 新しい関数・クラスを docs/REPO_MAP.md に反映
  4. 発見した教訓を docs/LESSONS_LEARNED.md に差分追記

Constraint（最小更新原則）:
  - 変更点のみを簡潔に反映する（全体書き直し禁止）
  - 「なぜその変更をしたか」という意思決定の背景を重視する
  - 「未来の自分（エージェント）への引き継ぎ事項」を1行添える
```

### 引き継ぎ事項のフォーマット

docs/LESSONS_LEARNED.md の末尾に以下を追記する：

```markdown
### 🔄 引き継ぎ事項 (YYYY-MM-DD)
> [次のセッションで最初に確認すべきこと、未解決の問題、注意点を1〜2行で記述]
```

## 1. オンボーディングフェーズ（新規ゲーム開始時）

### Step 1: プロジェクト構造の把握
- `project_analyzer` スキルを参照し、現在のプロジェクト構造を把握する
- 対象ゲームの `docs/` ディレクトリ内のドキュメントを確認する
  - `docs/PROJECT_STRUCTURE.md` が存在する場合はそれを読む
  - `docs/REPO_MAP.md` が存在する場合、関数・クラスの依存関係を確認する
  - `docs/LESSONS_LEARNED.md` が存在する場合、過去の教訓を参照する
- ルートの `GAME_REGISTRY.md` を確認し、既存ゲームとの重複や参考になる実装を確認する
- 存在しない場合は `project_analyzer` のスクリプトを実行して生成する

### Step 2: 設計計画書（Artifacts）の出力
- コードを1行も書く前に、`templates/game_plan_template.md` を参考にした設計計画書を `implementation_plan.md` として出力する
- 計画書には以下を含める：
  - ゲームコンセプトと仕様
  - 技術スタック（Canvas 2D / WebGL / Three.js 等）— `engine_rules` のフレームワーク親和性基準を参考に選定
  - ファイル構成（`engine_rules` の分割ルールに従う）
  - 主要クラス・モジュールの設計
  - 段階的な実装手順

### Step 3: ユーザーレビュー
- 計画書を `notify_user` でユーザーに提示し、レビューと承認を得る
- **承認前にコードの実装を開始してはならない**

## 2. 並列タスク分解フェーズ（マルチエージェント・オーケストレーション）

承認後、`templates/task_decomposition_template.md` を参考にタスクを分解する。

### マルチエージェント役割モデル

タスク分解は以下の4つの役割に基づいて行う：

| 役割 | 責務 | 対応フェーズ |
|------|------|------------|
| **Planner（設計者）** | 要件定義、アーキテクチャ設計、タスク分解 | オンボーディング |
| **Coder（実装者）** | 仕様に基づく特定コンポーネントのコード記述 | 実装 |
| **Reviewer（検証者）** | 生成コードの品質・パフォーマンス・セキュリティ分析 | テスト・QA |
| **Curator（記録者）** | 教訓の抽出、構造ファイルの差分更新 | ドキュメント更新 |

### 分解の原則
- **独立性**: 各タスクは他のタスクに依存せず独立して実行可能であること
- **明確な成果物**: 各タスクの完了条件と成果物が明確であること
- **コンポーネント指向**: 機能を独立モジュールとして設計し、段階的に統合する
- **コード品質**: `engine_rules` スキルのアーキテクチャ負債防止ルールに従うこと

### 典型的なタスク分解例

```
├── [Coder] タスク1: ゲームエンジン / コアループ (main.js)
├── [Coder] タスク2: プレイヤー操作ロジック (player.js)
├── [Coder] タスク3: 敵AI / ゲームロジック (enemy.js)
├── [Coder] タスク4: UI / HUD 構築 (ui.js)
├── [Coder] タスク5: ステージ / レベルデザイン (levels.js)
├── [Coder] タスク6: サウンド・エフェクト統合 (audio.js)
├── [Reviewer] タスク7: 統合テスト・QA
└── [Curator] タスク8: ドキュメント・教訓更新
```

## 3. 実装フェーズ

### Coder（実装者）のルール
- `engine_rules` スキルのルールに従い、ゲームエンジン固有のベストプラクティスを守る
- 各タスクの実装完了後、`task.md` のチェックリストを更新する

### 複雑性の壁（Complexity Wall）の回避策

> AIエージェントは個別コンポーネントの記述には優れているが、
> システム全体の統合では「複雑性の壁」に直面する。

この壁を回避するために、`engine_rules` スキルのアーキテクチャ負債防止ルールを厳守すること。
特に以下を意識する：

- **1ファイル最大300行** — 超過したら即座にモジュール分割
- **グローバル変数の使用禁止** — 明示的な `export`/`import` で依存を管理
- **ハードコーディング禁止** — 定数は設定ファイルに集約

> 📎 詳細なルールは [`engine_rules` スキル](file:///c:/Users/pusap/work/Antigravity-Games/.agent/skills/engine_rules/SKILL.md) を参照

## 4. テスト・QAフェーズ（Reviewer 役割）

- `auto_qa` スキルを参照し、以下を実行する：
  - ブラウザでゲームを起動し動作確認
  - スクリーンショット付きQAレポートの生成
  - パフォーマンス、レスポンシブ性の確認
  - コード品質の静的分析・セキュリティチェック

---

## 5. ドキュメント更新フェーズ（Curator 役割 / Context Architect State Persistence）

このフェーズはACEフレームワークの**Curator（キュレーター）役割**と
Context Architectプロトコルの**State Persistence**に相当する。

### 自動更新
- `project_analyzer` スキルのスクリプトを**ゲームプロジェクトディレクトリ**に対して実行する：
  - `docs/PROJECT_STRUCTURE.md` の再生成
  - `docs/REPO_MAP.md` の再生成（関数・クラスシグネチャのマップ）
  - ルートの `GAME_REGISTRY.md` に新しいゲームを登録

### 教訓の差分追記（Delta Updates）
- 開発中に発見したバグ、設計上の問題、回避策を `docs/LESSONS_LEARNED.md` に**差分追記**する
- **全体を書き直してはならない**（簡潔さのバイアスによる情報喪失を防止）
- 追記フォーマット：
  ```markdown
  ### [日付] [ゲーム名] - [教訓タイトル]
  - **問題**: （発生した問題）
  - **原因**: （根本原因）
  - **解決策**: （採用した解決策）
  - **教訓**: （今後のプロジェクトに活かすべき知見）
  ```

### 引き継ぎ事項の追記
- `docs/LESSONS_LEARNED.md` の末尾に**引き継ぎ事項**を追記する
- これにより次のセッション開始時に Context Sync で自動的に引き継ぎ情報を取得できる

### ウォークスルー作成
- `walkthrough.md` を作成し、実装内容をまとめる
